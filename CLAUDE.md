# Vibe Rooms

Flutter app where friends join a room with a 6-character code and listen to the same Audius track in sync, with a shared queue, live chat and emoji reactions. Must be demo-ready in one day: keep scope tight.

## Stack
- Flutter (Android primary, web for quick testing), Dart
- Supabase: Auth, Postgres, Realtime (`supabase_flutter`)
- State: `flutter_riverpod`; routing: `go_router`
- Audio: `just_audio`; Audius via `http`; images via `cached_network_image`
- Tests: `flutter_test`, `mocktail`

## Playback sync design
One Postgres row per room holds playback state (`track_id`, `is_playing`, `position_ms`, server-side `updated_at`). Every client listens through Supabase Realtime and computes its own position from the server timestamp.

## Folder conventions
Feature-first. Each feature (`auth`, `rooms`, `player`, `queue`, `chat`) lives in `lib/features/<name>/` with:
- `data/`: repositories and data sources
- `domain/`: models and pure logic
- `presentation/`: screens, widgets, providers

Shared code is in `lib/core/` (`config.dart`, `router.dart`, `theme.dart`, `supabase_client.dart`, `widgets/`). Keep a `.gitkeep` in empty folders.

## Rules
- **All Supabase calls go through repository classes in each feature's `data/` folder, never directly from widgets.**
- Riverpod for state. No business logic in widgets.
- Never commit secrets. `env.json` is git-ignored; `env.example.json` is the template.
- The app must not crash when Supabase is unconfigured (`config.isConfigured` is false): screens show a banner.

## Commands
- Run: `flutter run --dart-define-from-file=env.json` (web: add `-d web-server --web-port 8080` or `-d chrome`)
- Analyze: `flutter analyze` (must report zero issues)
- Test: `flutter test`
- Format: `dart format lib test`

## Database
SQL lives in `supabase/migrations/` (`0001_init.sql` runs once on an empty project; `0000_reset_dev.sql` deletes all app data and is for development only) and is run by hand in the Supabase SQL editor. Checks are in `supabase/tests/`: `verify_structure.sql` (one readable table) and `verify_behavior.sql` (simulates 3 users; expect an error starting with `VERIFY_OK`).

- **Tables** (public schema, RLS on all): `profiles`, `rooms`, `room_members`, `queue_items`, `room_state` (one row per room), `messages`. Dart models are in each feature's `domain/` folder.
- **Auth:** anonymous sign-in plus email; both use the `authenticated` role. A trigger creates the profile for every new user.
- **RPCs** (the only way to create or join a room): `create_room(p_name)`, `join_room(p_code)` (raises `room_not_found` / `P0002`), `server_now()` (clients use it to measure their clock offset). Clients cannot insert into `rooms`, `room_members` or `room_state`.
- **Host-only playback:** only the room host can update `room_state` (and mark queue items played). Guests can add queue items and chat.
- **Clients never set `updated_at`.** A trigger stamps `updated_at` and `updated_by` on every direct `room_state` update, and the column is not grantable. Send only `RoomState.toUpdateJson()`. Position = `RoomState.expectedPositionMs(serverNow)`, where `serverNow` is the local clock plus the offset from `server_now()`.
- **Column-level grants:** clients can write only the columns the app needs (for example `rooms` allows only `name` and `closed_at`); `queue_items.sort_key` is generated by the database.
- **Realtime:** `room_state`, `queue_items`, `messages`, `room_members` are published. DELETE events are not filtered by RLS and carry only the primary key, so remove rows by id.

## Auth
Guest (anonymous) and email sign-in through Supabase Auth, plus the user's profile. Code is in `lib/features/auth/`.

- **Repositories** (`domain/` interface, `data/` implementation; widgets never import Supabase): `AuthRepository` (`signInAsGuest`, `signUpWithEmail`, `signInWithEmail`, `signOut`, `isSignedIn`, `isAnonymous`, `userId`, `signedInChanges`) and `ProfileRepository` (`getMyProfile`, `updateMyProfile`; writes only `display_name` and `avatar_emoji`). They throw `AuthFailure` (a kind plus a short human message); `mapAuthError` in `data/` translates Supabase errors and logs unknown ones with `debugPrint`, never request data or passwords.
- **display_name convention:** the display name is sent as the `display_name` user-metadata key on sign-up and anonymous sign-in. The `handle_new_user` trigger reads it to create the profile row. `getMyProfile` creates the row itself if it is missing.
- **Providers** (`presentation/auth_providers.dart`): `authRepositoryProvider`, `profileRepositoryProvider`, `signedInProvider` (seeded with the current state) and `myProfileProvider` (autoDispose, rebuilt on every auth change so one user never sees another's profile; `save()` updates). `supabaseReadyProvider` (core) is overridden in `main` with the result of `initSupabase`; when false, the repositories are the `Unconfigured…` ones and nothing touches `Supabase.instance`.
- **Router redirects** (`core/router.dart`, `authRedirect`): signed out and not on `/login` goes to `/login`; signed in and on `/login` goes to `/home`. The rules are mutually exclusive, so they cannot loop. The router re-runs them through a `refreshListenable` fed by `signedInChanges`. Unconfigured, the router stays on `/login` and the login screen shows the "Supabase is not configured" message with the buttons disabled.
- **Validators** (`domain/validators.dart`): display name 1 to 30 characters after trimming (counted in code points, like the database), simple email check, password of 6 or more characters.
- **Tests** use `FakeAuthRepository` / `FakeProfileRepository` (`test/fakes/fakes.dart`) through `ProviderScope` overrides; no network. Import `package:material_ui/material_ui.dart` in tests, not `package:flutter/material.dart`, or widget finders will not match.

## Rooms
Create, join (code or link), list, leave and close rooms, plus the room screen with live presence. Code is in `lib/features/rooms/`. The Chat tab is still a placeholder (the Queue tab is built, see **Queue**).

- **Repositories** (`domain/` interface, `data/` Supabase implementation, `Unconfigured…` fallbacks; widgets never import Supabase): `RoomRepository` (`createRoom` and `joinRoom` call the `create_room` / `join_room` RPCs; `myRooms`, `getRoom`, `watchMembers`, `leaveRoom`, `closeRoom`) and `RoomPresence`. They throw `RoomFailure` (kind plus a short message); `mapRoomError` translates RPC errors (`room_not_found` / `P0002`, `invalid_name`, `not_authenticated` / `28000`) and logs only the error type and code, never messages, room codes or user ids.
- **Room codes** (`domain/room_code.dart`): alphabet `ABCDEFGHJKLMNPQRSTUVWXYZ23456789`, `normalizeRoomCode` (trim, upper-case, drop anything else), `isValidRoomCode` (exactly 6). The join sheet's `RoomCodeFormatter` applies the same rules while typing and pasting.
- **Visibility:** RLS hides rooms from non-members, so `getRoom` returns null for "does not exist" and "I am not a member" alike, and the room screen shows one friendly "Room not found" message. A closed room (`closed_at` set) shows "Room closed". `join_room` ignores closed rooms.
- **Members** (`watchMembers`): loads the list at once, then reloads (debounced) on every Postgres Changes event for `room_members` filtered by `room_id`, and again whenever the channel (re)joins, because events missed while offline are not replayed. Each member row embeds `profiles(...)` and `rooms(host_id)`. `roomProvider` re-reads the room whenever the member list changes: that is how members notice the host closed the room (the host sets `closed_at`, then leaves, which emits a DELETE).
- **Presence and the `RoomChannel` convention** (`data/room_channel.dart`): `room:<roomId>` is the room's presence channel, keyed by user id, announcing `{user_id, display_name, avatar_emoji}`. `track` runs inside the `subscribe` status callback, which fires on every rejoin, so presence survives reconnects. A channel can be subscribed only once and `channel()` does not de-duplicate by topic, so later features (playback sync, reactions) must add their listeners to the channel built by `RoomChannel.presence` before it is subscribed, never create a second channel for the same topic. Member changes use their own topic (`room-members:<id>`). Every stream releases its channel with `removeChannel` in `onCancel`, and guards late callbacks with a `closed` flag.
- **Providers** (`presentation/rooms_providers.dart`): `roomRepositoryProvider`, `roomPresenceProvider`, `myRoomsProvider` (autoDispose; invalidate after create, join, leave and close), `roomProvider(id)`, `roomMembersProvider(id)`, `onlineUsersProvider(id)` (reads the profile once, so editing it does not rejoin the channel).
- **Routes:** `/room/:id` and `/join/:code` (spinner, joins, then replaces itself with `/room/<id>`; a failure goes to `/home` with a snackbar). Leaving or closing shows a spinner until navigation, so the room does not flash "not found" in between.
- **Redirect rule** (`core/redirect.dart`, `authRedirect`): a deep link opened while signed out becomes `/login?from=<path>`, and after sign-in the user goes to `from`. Only an allowlist is accepted (`/home`, `/room/<id>`, `/join/<code>`: no scheme, no `//`, no `%`, no query), anything else goes to `/home`. After an explicit sign-out `from` is not kept, so the next person to sign in is not sent to the previous person's room. The rules cannot loop (tested).
- **Invites:** "Copy invite" copies `Join my Vibe Room "<name>" with code <CODE>` and, on web only, the link `<origin>/#/join/<CODE>`.

## Music and player
Search and playback of Audius tracks. Code is in `lib/features/player/`. What plays is decided by the room's playback row (see **Sync** below); this section covers the catalog, the engine and the search sheet.

- **Catalog** (`MusicCatalog`, `data/audius_catalog.dart`): the Audius public API at `https://api.audius.co/v1` (`/tracks/search?query=&limit=`, `/tracks/trending?limit=&time=week`, `/tracks/<id>/stream`). No key is needed and there is no host discovery (the host list is a single entry); `hosts` is still an ordered list with failover. Plain GETs without custom headers (no CORS preflight), 8 s timeouts, one retry with backoff on 429/5xx/timeout/network error (`Retry-After` honoured up to 2 s), failures mapped to `AudiusFailure`, trending cached for 2 minutes. `app_name=vibe_rooms` is always sent. An optional `AUDIUS_API_KEY` in `env.json` is sent as `api_key` when non-empty (untested: the API ignores keys on these endpoints today; it must be a client-side key, never a bearer token). URLs, queries and keys are never logged.
- **Parser** (`data/audius_parser.dart`): never throws. Skips deleted, unlisted, non-streamable and stream-gated tracks and tracks without a positive duration. Artist is `user.name`, then `user.handle`, then "Unknown artist".
- **`Track` validation** (`domain/track.dart`): a `Track` can never hold a value the `queue_items` table would reject. `durationMs > 0` (else `ArgumentError`; use `Track.tryCreate` for null), `id` at most 100, `title` and `artist` at most 300 characters (cut by code point, trimmed), `artworkUrl` and `permalinkUrl` only if `https`, whitespace-free and at most 2048 characters. `toQueueInsertJson(roomId, addedBy)` has exactly the `QueueItem.toInsertJson` shape. Track data is external and untrusted: render it with `Text` only, and only ever open `https://audius.co/...` links.
- **`AudioEngine`** (`domain/audio_engine.dart`) is the seam for synced playback and for tests. Contract: `load` never throws (failure becomes the `error` phase) and a superseded `load` finishes silently; `play` and `playFrom(position)` (seek, then play) return as soon as the command is issued, they do NOT wait for the track to end (just_audio's own `play()` does); `position` is the best current estimate and can be sampled at any moment; `setSpeed` corrects drift without an audible seek; after `dispose` audio has stopped. `JustAudioEngine` implements it; `FakeAudioEngine` (`test/fakes/fakes.dart`) drives the tests.
- **Engine ownership:** `SyncController` (see **Sync**) is the only thing that drives the engine in a room. It gets one from `audioEngineFactoryProvider` (a factory, so every room visit gets a fresh engine; a plain provider would hand out a disposed one). Leaving the room disposes the controller, which disposes the engine and stops the audio (verified in the browser on the real `<audio>` element). The old local-only `PlayerController` was removed.
- **Sound gate** (`soundEnabledProvider`, `SoundGate`): browsers block audio until the user taps something. On web `soundEnabledProvider` starts false and the "Tap to turn on sound" banner turns it on (sticky user activation then allows later `play()` calls even after network awaits); elsewhere it starts true. The planner enforces it too (`WaitForSoundGate`), not just the UI. It resets when the user leaves the room. `soundGateRequiredProvider` (true on web) is overridable in tests.
- **`TrackSearchSheet`** (`presentation/track_search_sheet.dart`): reusable, takes `onTrackSelected(Track)` (in a room it is the host's `hostSetTrack`) and a title, and knows nothing about rooms or the database. 400 ms debounce; every keystroke bumps a generation counter so a slow, stale response can never overwrite a newer one; empty field shows trending (kept watched, so clearing is instant); loading, "No tracks found" and error + Retry states.
- **Attribution:** the player card shows the artist and "Music via Audius". The "Open on Audius" link is gone: `room_state` stores no permalink, so listeners have nothing to link to. The Open Music License only obliges commercial licensees (artist, copyright notice, a notice referring to the OML, a hyperlink to the track "to the extent reasonably practicable"); add the copyright and OML notices before any commercial use.
- **`Track.toQueueInsertJson`** feeds the queue step.
- **Test gotcha:** `EnginePhase` also exists in `flutter_test`; import it as `import 'package:flutter_test/flutter_test.dart' hide EnginePhase;` in tests that use our enum.

## Sync
Synchronized playback: the host controls the music, everyone hears the same track at the same position. Code is in `lib/features/player/` (`domain/` pure logic, `data/` Supabase, `presentation/sync_controller.dart`).

**Anchor semantics.** The `room_state` row means: "at SERVER time `updated_at`, the position was `position_ms` and playback was `is_playing`". Postgres sets `updated_at` (trigger), clients never can. Expected position now = `RoomState.expectedPositionMs(serverNow)`, clamped to the duration. A device clock is never used on its own to read `updated_at`.

```
 room_state row ──► planSync(row, engine, server clock) ──► ONE SyncAction ──► AudioEngine
      ▲                          ▲
  Realtime UPDATE        ServerClock: 5 x server_now(),
  + refetch on rejoin    keep the smallest round trip
```

- **`ServerClock`** (`domain/server_clock.dart`): per sample `offset = serverTime + rtt/2 - localReceiveTime`; the smallest-rtt sample of 5 wins. `nowServer()` = local clock + offset. A failed measurement keeps the old offset; a much worse one (rtt over 3x the old plus 100 ms) does not replace a good measurement younger than 5 minutes. Measured on room entry, every 60 s, on app/tab resume and after a realtime reconnect. Until the first success nothing is planned.
- **`RoomStateRepository`** (`domain/`, `data/supabase_room_state_repository.dart`, `Unconfigured` fallback): `get`, `watch`, `hostUpdate`. `watch` reads the row, then listens to Postgres Changes UPDATE on its own channel `room_state:<roomId>`, and reads again on every (re)join. Stale rule: an event with an `updated_at` strictly older than the newest seen is dropped. Equal is kept (a foreign-key `on delete set null` changes the row without moving `updated_at`, risk 11), an identical row is not emitted twice. Channel trouble is a stream error (the stream stays open), which the controller shows as "Reconnecting...". `hostUpdate` uses `.update(...).select('room_id')` and an empty result (row level security) throws `RoomStateFailure(notAllowed)`. `RoomStateUpdate` never contains `updated_at`, `updated_by` or `room_id`. The raw calls sit behind `RoomStateSource` so the rules are tested without a network. `ServerTimeSource` wraps the `server_now()` RPC.
- **`planSync`** (`domain/sync_planner.dart`) is a pure function returning exactly one action: `None`, `WaitForSoundGate`, `LoadThenPlay`, `Play(seekTo)`, `Pause(seekTo)`, `Seek(to)`, `Ended`. Order: no row or track -> None; playing and expected >= duration -> Ended (nothing is loaded for a finished track); other track than loaded -> LoadThenPlay; engine error -> LoadThenPlay (the controller throttles retries to one per 5 s); engine loading or buffering -> None (its position means nothing, so no seek storm); playing room: no sound -> WaitForSoundGate, engine not playing -> Play(expected) (an engine that completed within 2.5 s of the end is Ended, not a restart), playing with drift beyond the threshold -> Seek(expected) unless the thrash guard blocks it; paused room: engine playing -> Pause(position_ms), engine far from `position_ms` -> Seek.
- **`SyncController`** (`presentation/sync_controller.dart`, `syncControllerProvider`, autoDispose family keyed by `(roomId, isHost)`): owns the engine, the clock, the repository subscription, three timers (drift check 2 s, display tick 500 ms, clock 60 s) and a resume observer. Actions are serialised: a request that arrives while one runs sets a flag and the loop plans again when it finishes. `LoadThenPlay` only loads; when the load is done the loop plans again with FRESH server time, so a track that took 2 s to load still starts at the right position. `Play` starts `seekCost` ahead, an average of how long the last `playFrom` calls took. After the first play following a load, one more drift check runs after 1.5 s with the thrash guard cleared, because seeks on streamed MP3 land imprecisely. A new row with a different `updated_at` (a host action) clears the thrash guard, because following the host is not thrash. Leaving the room disposes the engine, cancels the subscription and every timer, and removes the observer.
- **`SyncStatus`** (chip): inSync, syncing, reconnecting, waitingForSound (the chip is also the web sound gate button), ended. `SyncDebug` holds server offset, rtt, last drift and last action.

**Constants** (`domain/sync_config.dart`, one `SyncConfig`):

| Constant | Value | Why |
|---|---|---|
| `driftThresholdMs` | 300 | Seeks on streamed MP3 are imprecise and slow; smaller drift is cheaper to live with than to fix |
| `driftHardLimitMs` | 2000 | Beyond this a correction is allowed inside the thrash guard window |
| `driftCheckInterval` | 2 s | Cheap comparison, no network |
| `minSeekGap` | 5 s | Every seek re-hits the Audius 302 (10 requests per second on the free plan) |
| `hardSeekGap` (extra) | 1 s | Even a hard correction waits, so a broken engine cannot seek every tick |
| `clockRemeasureInterval` | 60 s | Bounds the damage of a stepped device clock |
| `postLoadDriftCheck` | 1500 ms | The first seek after a load can land imprecisely |
| `clockSamples` | 5 | Smallest round trip of five is accurate enough |
| `maxLatencyCompensationMs` (extra) | 1500 | One bad rtt measurement must not skew the whole room |
| `endToleranceMs` (extra) | 2500 | Audio can end a little before the stored duration |
| `reloadGap` (extra) | 5 s | Retry pace after a load error |
| `displayTick` (extra) | 500 ms | Refresh of the shown position |

**Host controls.** `isHost` is `room.hostId == my id`; the database enforces it too (RLS), the UI check is for display. `hostSetTrack` writes the track columns with `position_ms` 0 and `is_playing` true (and unlocks sound: picking a track is a tap). `hostTogglePlay` pause writes the engine's position; resume writes the position plus half the round trip; a restart after the end begins at 0. `hostSeek` is written on slider release only. Writes are optimistic: the host's own state and engine follow at once, and the echo then finds drift below the threshold and does nothing; a failed write is undone only if nothing newer arrived meanwhile, and explained. **Latency compensation:** the server stamps `updated_at` when the write ARRIVES, so a write made while playing adds `min(rtt / 2, 1500)` to `position_ms`; `setTrack` and writes while paused add nothing. At the end of the track the host handles it once per anchor (also when the engine completes slightly early): the queue's `onTrackEnded` hook starts the next song, and without a hook (or with an empty queue) `hostEnd()` writes `is_playing` false and `position_ms` = `duration_ms`. A handler result of `failed` clears the once-per-anchor mark so a later tick retries; `ignored` (the room already moved on) does not write anything.

**Listeners** have no transport controls: a read-only progress bar, a local Mute (engine volume), and the sound gate. The card shows the track from the row, and the position from the server clock, so everyone sees the same time. A late joiner sees "Music is playing. Tap to join in".

**Debug panel.** A collapsible "Sync debug" card (status, offset, rtt, drift, last action, host) shown in debug builds (`debugPanelDefaultProvider`) or after tapping the room name five times.

**Test harness.** `FakeRoomStateRepository` (the test plays the server: `emit`, `autoEcho`, `failNext`, `writes`), `FakeServerTimeSource` (skew, rtt), `FakeAudioEngine` with a `clock` (position advances while playing), `loadDelay`, `seekDelay` and `maxInFlight`. Timing tests use `fake_async` (`test/player/sync_controller_test.dart`).

## Queue
The shared queue. Code is in `lib/features/queue/` (plus `TrackTile` and the search sheet's add mode in `lib/features/player/presentation/`).

**Model: consumed on start.** An item is "upcoming" while `queue_items.played_at` is null. The now-playing song comes from `room_state` (and its `queue_item_id`), never from the list. An item is consumed (`played_at` set) when it starts playing. The queue SQL is unchanged: members select and insert (`added_by` = me), the host updates only `played_at`, the host or the adder deletes.

- **`QueueRepository`** (`domain/`, `data/supabase_queue_repository.dart`, `Unconfigured` fallback): `upcoming` (`played_at is null`, ordered by `sort_key`, embeds `profiles(display_name, avatar_emoji)` for "added by"), `watchUpcoming`, `add` (inserts exactly `Track.toQueueInsertJson`), `remove`, `markPlayed(id, at)` (null un-marks). `remove` and `markPlayed` use `.select('id')` and an empty result (row level security) throws `QueueFailure(notAllowed)`. `watchUpcoming` reloads the whole list (it is at most 50 rows) on ANY change in `queue_items` for the room (debounced 250 ms, one load at a time so an older answer never overwrites a newer one) and again on every channel rejoin, on its own topic `queue:<roomId>`; channel trouble is a stream error and the stream stays open. Raw calls sit behind `QueueSource` so the rules are tested without a network. DELETE events carry only the primary key, which is why it reloads instead of patching.
- **`QueueFailure`**: full, duplicate, notAllowed, network, unknown, each with a short message ("Already in the queue", "The queue is full (50 songs).", "You already have 10 songs queued. Wait for one to play.").
- **Client-side limits** (`domain/queue_limits.dart`; the database does NOT enforce them): 50 upcoming per room, 10 per user, no track already upcoming in the room. `add` checks against a FRESH `upcoming()` read, not the list on screen. `visibleUpcoming` is the one function that hides the item playing right now; the list, the limits, the duplicate check and Next all go through it (`visibleUpcomingProvider`).
- **`QueueController`** (`presentation/queue_controller.dart`, `queueControllerProvider(SyncArgs)`, autoDispose): `add`, `remove` (host or adder, refused locally for others), and for the host only `playNext`, `playItem` and the end-of-song hook. `SyncController` stays the only writer of `room_state` (`hostAdvanceTo(item)`, `hostEnd()`).
- **Advance sequence (host only, one at a time):**

```
pick target (fresh list) ──► write room_state: item's track, queue_item_id, position 0, playing   <- the commit point
                                  │ fails: nothing changed, nothing to undo, a message is shown
                                  ▼
                         mark target played, and the item that just finished (best effort)
                                  │ fails: the item is playing but unmarked; hidden by id everywhere,
                                  ▼        healed by _reconcile on the next change, and by the next advance
```

  The room row is written FIRST (the reverse of "mark, write, roll back"): a crash or a lost connection can leave an item that is playing but not marked, never one that is marked but was never played, and there is no rollback that can itself fail. `_reconcile` acts once per item (a failed mark is forgotten so it is retried) and never during an advance, so it cannot loop with the events it causes. `playItem` first checks the item is still upcoming ("That song is no longer in the queue."). `playNext` on an empty queue writes the ended state.
- **Double advance.** (1) An in-flight guard (`advancing`) serialises Next, Play now and the automatic advance, and disables the buttons. (2) The end-of-song hook (`SyncController.onTrackEnded`, `TrackEndResult` advanced / ignored / failed) advances only if the room row STILL shows the same ended song (same `track_id` and `updated_at`), so a skip tap and the natural end consume one item. If a skip is running when the song ends the hook answers `failed`, so the end is retried on a later tick. (3) There is no compare-and-swap in the database (see risk 60).
- **Hardening from /review and /cso.** Every repository call has a 10 s timeout (a hung request would otherwise freeze the reload loop and leave `advancing` stuck); the upcoming query is bounded (`.limit(200)`); one unreadable row is skipped instead of breaking the list; a `subscribe` that throws becomes a stream error. The host skips (and consumes) any item shorter than 5 s or longer than 6 h (`isPlayableLength`): the length is written by the member who added the item, and the host uses it to decide when a song ended. The host also remembers the items it started (`_started`) and never offers them again, even if marking them played keeps failing. The queue's realtime channel is kept alive by the room screen, not by the Queue tab.
- **Play now from search** (`hostSetTrack`) keeps writing `queue_item_id` null and does not touch the queue.
- **Screens.** The Queue tab (`queue_tab.dart`) shows "Up next (N)" with "Add songs", a pinned "Now playing" row read from `room_state`, then flat rows (`TrackTile`: artwork, title, artist, "Added by 🎸 Bo", length). The host has "Play now" on every row; the host and the adder have a remove button; loading is skeleton rows, empty is "Nothing queued. Add songs with Find music.", errors have Retry. The player card has a host-only "Next" (disabled while an advance runs and when nothing is queued) and, in an idle room with songs queued, "Play next". The search sheet's add mode (`onAdd`, `onPlayNow`, `queuedTrackIds`; no room or database code inside) adds with "+", shows "Added", stays open, shows failures in a snackbar, and offers the host "Play now". Its own `Scaffold` makes the snackbar show above the sheet (the page's messenger shows a second copy behind it).
- **Test harness.** `FakeQueueRepository` (the test plays the database: `externalAdd`, `failNextAdd`, `failAllMarks`, `markGate`), `fakeQueueItem`. Timing tests use `fake_async` (`test/queue/queue_controller_test.dart`).

## Known risks

Raised by /plan-eng-review (condensed, risks-only run; design and build order accepted unchanged).

1. **Clock skew and `updated_at`.** `updated_at` must be set by Postgres (a `now()` default plus a before-update trigger), never by the client. Clients also need a server-time offset (RPC returning `now()`, corrected by half the round trip). Computing position from the device clock breaks sync on any phone with a skewed clock.
2. **Seek and drift on streamed audio.** `just_audio` seeks on a not-yet-buffered Audius MP3 stream are imprecise and slow. Re-seek only when drift exceeds a threshold (about 300 ms) and ignore small drift, or playback will stutter.
3. **Web autoplay policy.** Browsers block audio until a user gesture. A joiner on web cannot auto-start in sync, so show a "Tap to join the music" gate before the first play.
4. **Audius stream URLs.** Resolve a host from the Audius discovery endpoint at runtime, pass an app name, and expect redirects, occasional 4xx and rate limits. Handle a track that fails to load without crashing the room.
5. **Realtime setup and reconnects.** The playback table must be in the `supabase_realtime` publication. After any reconnect or app resume, re-read the row, because missed events are not replayed.
6. **RLS and room join.** Every table needs RLS from step 2. Join-by-code should go through an RPC or a narrowly scoped policy, not a world-readable rooms table. 6-character codes need a uniqueness constraint and a retry on collision. Anonymous sign-in must be enabled in the Supabase dashboard.
7. **Concurrent control.** Two users pressing play or seek at once is last-write-wins. Decide in step 6 whether only the host controls playback (simplest, recommended for the demo).
8. **Reactions volume.** Emoji reactions should use Realtime Broadcast (ephemeral), not Postgres rows. Chat messages persist and need pagination or a limit.
9. **Android release build.** `flutter create` puts the INTERNET permission only in the debug and profile manifests. Add it to the main `AndroidManifest.xml` before building a release APK, or the app has no network. Local `flutter doctor` also reports unaccepted Android licenses.
10. **Schedule.** Step 6 (synced playback) is the riskiest step. Timebox it, and keep steps 7 and 8 as the cuttable scope if the day runs short.

Added by the database-layer /plan-eng-review:

Added by the sync /plan-eng-review:

47. **Fixed in the design:** the stale-event rule is "strictly older" (an equal `updated_at` can carry a foreign-key change); drift is never corrected while the engine is loading or buffering (a stalled position would look like huge drift and cause a seek storm); a hard-limit seek still waits 1 s after the last seek; the one extra drift check after a load clears the thrash guard (it would otherwise block exactly that correction); a new host action clears the thrash guard; `playFrom` starts a measured seek cost ahead; a much worse clock measurement does not replace a good recent one; latency compensation is capped at 1.5 s and not applied to `setTrack`; the host also treats an engine that completed within 2.5 s of the end as the end (Audius `duration` and the real audio length can differ); the host's play and pick-track taps unlock web sound; `AudioEngine` gained `setVolume` for the local mute. Found in review: a failed host write undid the optimistic state even if a newer server row had arrived meanwhile (now it only undoes its own change).
48. **Clock accuracy has a floor.** The offset assumes the two legs of `server_now()` take equal time; an asymmetric mobile network can bias it by up to half the round trip (measured here: rtt 237 ms to Supabase). The smallest-rtt sample of five limits this but cannot remove it. The browser drift numbers (median 4 ms, max 97 ms) come from two sessions on ONE machine, so they share a device clock and a network path: clock skew is covered by unit tests (plus and minus 5 minutes), not by the browser run, and real phones on mobile data will be worse.
49. **Latency compensation uses the `server_now()` round trip as a proxy** for the write's one-way delay. The write path (PostgREST, RLS, trigger) can be slower, so the host's write anchor is slightly early or late; the drift correction absorbs it above 300 ms only.
50. **Only the host's tap unlocks sound for the host.** A listener on web still needs the gate tap before audio starts (Safari and iOS untested, risks 3 and 40). Listeners in a background browser tab may have audio paused by the browser; the resume handler re-syncs when the tab returns.
51. **Android background playback and audio focus are still not handled** (risk 41), so sync on a locked phone is best effort. Android resume after a long time in the background is untested (risk 33); the resume handler re-measures the clock and re-reads the row.
52. **A host who leaves or loses the connection strands the room** (risk 15): the row keeps saying "playing", so listeners run to the end of the track and show "Ended". There is no heartbeat or host transfer.
53. **The artwork URL in `room_state` is written by the host** and every listener's client loads it. The database caps it (https, 2048 characters) but cannot restrict the host, so a malicious host in a room could point it at a server that logs listener IPs. Audius content nodes run on many domains, so a client-side allowlist is not practical; track title and artist are only ever rendered as text.
54. **The Audius rate limit is shared by all listeners behind one IP.** Each load and each seek costs a 302 request; the thrash guard limits one client to about one seek per 5 s, but a whole venue on one network joining at once can still trip 10 requests per second (a failed load is retried every 5 s).
55. **`room_state` events are public to the realtime server's RLS only.** Postgres Changes UPDATE events for `room_state` respect RLS (members only), unlike DELETE events (risk 12), and `room_state` rows are never deleted by clients. The presence channel is still public (risk 32).
56. **Seek cost compensation is an average** of the last `playFrom` durations (capped at 1.5 s). A track whose first seek is much slower than later ones can start late; the 1.5 s post-load check corrects it.
57. **The five-tap debug unlock is not a security control**; the panel shows only local sync numbers, no ids or secrets.

Added by the queue /plan-eng-review (the outside voice was a same-family Claude subagent: Codex is not installed):

58. **Fixed in the design:** the advance writes the room row first and marks played second (the original "mark, write, roll back" could lose a song when the rollback itself failed); every advance also marks the item that just finished and the host reconciles an item that is playing but unmarked, so it cannot replay later; one shared `visibleUpcoming` hides the playing item for the list, the limits, the duplicate check and Next; the limit check reads a fresh list; `playItem` re-checks the item; a skip in flight makes the end-of-song hook answer `failed` (retry), a moved-on room answers `ignored` (never overwrite). Found in testing: a failed mark was remembered as done, so the reconcile never retried it.
59. **The limits are client-side only** (50 per room, 10 per user, no duplicate upcoming track). The SQL is frozen, so a modified client can add as many rows as it likes, and two members adding at the same moment can both pass the check. Add a trigger or check constraint when the SQL may change.
60. **A double advance is guarded, not prevented.** Two host tabs (or devices) are two clients that both detect the end of a song; the in-flight guard and the row comparison are per client. A database-side compare-and-swap (`.eq('updated_at', ...)`) was rejected: on web Dart has millisecond precision while Postgres has microseconds, any host write bumps `updated_at` (so a seek between decision and write would abort the advance), and nothing defines who retries. In the browser run, with two host tabs in one room, exactly one advance happened, but one run does not prove the race cannot occur.
61. **The advance runs only while the host's client does.** A backgrounded or throttled host tab or phone does not advance when the song ends, and the room sits in "Ended" until the host returns (extends risk 52).
62. **Any member controls an artwork URL.** A queue item's `artwork_url` is written by the adder (the database checks only https and 2048 characters), and every member's client loads it, so a member can point it at a server that logs the IPs of the whole room (extends risk 53, which was host-only). Titles and artists are only ever shown as `Text`.
63. **Played rows are never deleted.** `played_at` is set and the row stays, so a long-lived room accumulates rows (the `room_id, sort_key` index keeps the upcoming query cheap).
64. **Adding a song to an idle or ended room does not start it.** The host sees "Play next" (empty player) or "Next"; nothing auto-starts, by design.
65. **There is a gap between songs on listeners** (they load the next track only when the row changes; roughly 1 to 3 seconds). No preloading.
66. **The duplicate rule checks upcoming items only**, so the song that is playing can be queued again.
67. **Reload-on-any-event costs one query per change** (debounced 250 ms): fine for 50 rows, not for large queues. Realtime DELETE events are not filtered by RLS (risk 12): they only trigger a reload.

68. **Found by /review and /cso (fixed):** a hung request froze the queue and the host's Next (timeouts added); a member-written `duration_ms` of 1 made the host skip the whole queue, and a huge one stalled the room (length bounds added); a persistently failing mark could replay an item (the host now remembers what it started); the Queue tab dropped and rejoined the realtime channel on every tab switch.
69. **Not fixed (needs a decision): member-controlled artwork.** `artwork_url` in a queue row is chosen by whoever adds it (the database checks only https and length) and every member's client fetches it, so a member with a modified client can learn the IP address of everyone in the room. A client allowlist is not practical: in a sample of 150 Audius results the artwork came from more than 12 third-party content-node domains (`monophonic.digital`, `figment.io`, `audiusindex.org`, `open-audio-validator.com`, `theblueprint.xyz`, `audius.co`, ...) and the set changes. Options: an allowlist that blanks unknown hosts, or a database check when the SQL may change.
70. **Member-written title, artist and track id are not tied to the audio.** A member can queue a title that does not match the `track_id` that plays (the stream URL is built with path segments, so there is no path injection). The host's "Now playing" row shows what the row says. Re-resolving the track from the catalog on advance would fix it at the cost of one API request per advance.
71. **`remove` and `markPlayed` of a row that is already gone** look like a permission failure to the database contract (an empty result); `remove` now says "That song is no longer in the queue." Foreign-key races (23503) fall to "unknown" and are retried by the end-of-song handler.
